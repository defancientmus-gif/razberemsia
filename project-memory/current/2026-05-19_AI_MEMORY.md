# Разберёмся — AI Memory

Последнее обновление: 2026-05-19

## Текущее решение

На текущем MVP AI-память хранится просто:

- локально: scoped `localStorage` key `rz_<user_id>_ai_memory`;
- облако: колонка `public.user_state.ai_memory jsonb not null default []`.

Это намеренно проще, чем отдельные таблицы. Сейчас важнее не сломать заметки и быстро проверить механику памяти.

## Что хранить

Хранить короткие выжимки, не весь сырой текст:

```json
{
  "id": "mem_...",
  "note_id": "note id or null",
  "cluster": "personal | project | feedback",
  "summary": "короткая суть",
  "importance": 1,
  "accepted": true,
  "tags": ["тег"],
  "created_at": "2026-05-19T..."
}
```

## Что уже есть в клиенте

- `getAiMemory()`
- `_saveAiMemoryRaw()`
- `addToAiMemory(summary,tags,noteId)`
- `getAiMemoryContext()`
- загрузка/сохранение `ai_memory` вместе с `notes/trash/history/name`;
- fallback на старую схему, если Supabase ещё не знает колонку `ai_memory`.

## Кластеры

Минимум:

- `personal` — личные планы, здоровье, семья, покупки, тревоги, идеи;
- `project` — мысли о развитии `Разберёмся`, баги, UX, Supabase, AI, промты;
- `feedback` — принята/отклонена подсказка AI.

Проектный кластер нужен, потому что пользователь часто пишет идеи о самом продукте. Эти мысли должны помогать обновлять TODO, changelog и мастер-контекст, но не смешиваться с личными заметками.

## Будущая архитектура

Отдельные таблицы возможны позже:

- `ai_memory`;
- `note_analysis`;
- `project_memory`;
- `memory_events`;
- `profiles` с флагом разработчика.

Не делать это прямо сейчас без отдельного решения. Нормализация базы полезна, но не должна ломать ядро заметок.

## Правило миграций

Любая новая колонка/таблица требует:

1. SQL в `supabase.sql` или отдельной migration-папке.
2. Совместимый клиент или порядок “сначала база, потом клиент”.
3. Проверка живого сценария заметок.
