# Чертёж репозитория — операционный костяк проекта «Женя + Инженер»

> Переносимый шаблон. Скопируй в новый репозиторий (БУ.шка, CRM, любой) и заведи проект
> на той же системе, что и «Разберёмся». Это не про код продукта — это про то, КАК мы вместе
> работаем, чтобы любая сессия стартовала с холода и была полезной за минуты.

---

## 0. Зачем это всё (философия системы)

Репозиторий — не только код. Это **общий мозг визионера и инженера, который переживает потерю
контекста**. У нас два врага:
1. Инженер теряет нить между сессиями (контекст обнуляется — память должна его вернуть).
2. Человек тонет в рутине (продукт и процесс должны снимать работу, а не добавлять).

Костяк ниже лечит оба: слои памяти + ритуалы + правила. Чем дисциплинированнее костяк —
тем больше высоты остаётся на собственно идеи.

---

## 1. Роли и правила общения

- **Визионер** видит образ, чувствует направление, говорит метафорами-ТЗ.
- **Инженер** переводит образ в код, находит решение, **сам предлагает следующий шаг**.
- Инженер НЕ ждёт технического направления, не спрашивает разрешения на очевидное.
- Замечает баг рядом с задачей — чинит сразу, упоминает мимоходом.
- **Отчитывается смыслом, а не жаргоном:** не «убрал box-shadow из keyframes», а «телефон останется холодным».
- **Не говорим НЕТ** — всегда позитивный исход (исключение: реальный вред).
- **Сначала назначение, потом форма.** Не закапываться в пиксели, теряя «что/где/почему».
- **Визуальные правки — показать до деплоя.** Образ/макет → «ок?» → сборка.
- Ошибся — признаёшь прямо, находишь корень, восстанавливаешь нить.

---

## 2. Архитектура репозитория

```
/                          # код продукта (фронт/бэк) живёт в корне или своих папках
  CLAUDE.md                # КОНСТИТУЦИЯ проекта — грузится в каждую сессию
  deploy.sh                # ЕДИНСТВЕННЫЙ путь деплоя (bump версии → commit → push)
  scripts/                 # автоматизация + smoke-тесты критичных путей
  texts/                   # АКТИВНАЯ ПАМЯТЬ (слоёный мозг, см. §3)
  texts/archive/           # холодная память — читать только по запросу
```

**CLAUDE.md** — конституция. Роли, дух продукта, стек-справочник, жёсткие правила,
ритуал сессии, «текущее состояние». Короткая, без воды — она грузится ВСЕГДА.

---

## 3. Архив контекста (texts/) — слои памяти по частоте чтения

**🔥 Горячее (читать в начале КАЖДОЙ сессии):**
- `README.md` — карта активной памяти: что где лежит.
- `ROUTER.md` — маршрут под тип задачи: «правишь X → читай файлы A, B».
- `SNAPSHOT.md` — **факты, а не желания**: версия деплоя, что живо, открытые риски. Источник правды о состоянии.
- `NEXT.md` — текущая задача + контекст прошлой сессии + принятые решения. **Обновляется в конце каждой сессии.**
- `TEST_GRID.md` — что проверять после правок (чек-лист регрессий).

**🌤 Тёплое (под конкретную задачу):**
- `UI_PHILOSOPHY.md` (или `DESIGN.md`) — визуальные/UX-законы, «что НИКОГДА не делать». Читать перед любой правкой вида.
- `RULES.md` — жёсткие правила (безопасность и пр.), вынесенные отдельно.
- `TERMINOLOGY.md` — общий словарь (чтобы не путаться в названиях).
- `PROJECT_CARD.md` / `CONTEXT.md` — что это за продукт, для кого, тип приложения, стек.
- `TECH_PROMPT.md` / `MASTER_PROMPT.md` — переносимый системный промпт (душа всей системы).

**🧊 Холодное (по запросу):**
- `IDEAS_NEAR_TERM.md` / `IDEAS_FUTURE.md` / `IDEAS_DONE_OR_DORMANT.md` — бэклог идей по горизонту.
- `LEAP_MAP.md` / research-доки — стратегия, разведка.
- `PERF_AUDIT.md` — аудиты.
- `archive/` — устаревшая память; не активный источник.

**Принцип:** слои по частоте чтения. Горячее — каждую сессию, тёплое — под задачу,
холодное — только когда спросили. Не раздувать горячий слой.

## 4. Ритуал сессии

**Начало:**
1. README → ROUTER → SNAPSHOT → NEXT → TEST_GRID.
2. `git status --short --branch`.
3. Дальше — только файлы под конкретную задачу.

**В процессе:**
- Перед правкой вида — перечитать UI_PHILOSOPHY (особенно «что НИКОГДА»).
- Перед правкой функции — grep по ВСЕМ файлам кода (дубли — частый враг).
- Начинать с точечных команд (`rg`, `sed`, `git status`), не широких.

**Конец:**
- Обновить `NEXT.md`: что сделано, что следующее, какие решения приняты и почему.

## 5. Деплой и безопасность

- **Один скрипт деплоя.** `deploy.sh`: поднять версию кэша/сборки → закоммитить нужные файлы → push.
  Не «git add -A вслепую» — только нужное.
- **Серверная логика (AI, секреты) деплоится ОТДЕЛЬНО** и фиксируется в SNAPSHOT.
- **Жёсткие правила (нельзя нарушать):**
  - Не класть API-ключи / service-ключи в клиент.
  - Не отключать защиту данных (RLS и т.п.).
  - AI/секретные вызовы — только через серверную функцию, не из клиента.
  - Внешние библиотеки **вендорить локально** (CDN-зависимость ломает офлайн и крадёт скорость).
- **Авто-проверки перед деплоем:** синтаксис (`node --check`), whitespace (`git diff --check`),
  smoke-тесты критичных путей (`scripts/smoke-*.mjs`). Smoke обязателен после правок ядра логики.

---

## 6. Память ассистента (auto-memory, вне репозитория)

Живёт в личной памяти инженера (переживает ВСЕ проекты): один факт = один файл + индекс `MEMORY.md`.
Типы: `user` (кто визионер), `feedback` (как работать — с «почему»), `project` (цели/ограничения),
`reference` (ссылки). Перед записью — проверить дубль; неверное — удалять. Не дублировать то,
что и так в репозитории (структуру кода, историю git).

---

## 7. Завести новый проект на этой системе (чек-лист)

1. `CLAUDE.md` — скопировать шаблон, адаптировать роли/стек/жёсткие правила.
2. `texts/` — создать: README, ROUTER, SNAPSHOT, NEXT, TEST_GRID, RULES, UI_PHILOSOPHY, TERMINOLOGY, PROJECT_CARD.
3. `deploy.sh` — единый деплой с bump версии.
4. `scripts/` — smoke-тесты под критичные пути продукта.
5. `NEXT.md` — засеять первой задачей.
6. `MASTER_PROMPT.md` / `TECH_PROMPT.md` — перенести «душу» (роли, дух, дизайн-язык, словарь метафор).
   Эталон — `TECH_PROMPT.md` из «Разберёмся».

---

## 8. Анти-паттерны (выучено кровью на «Разберёмся»)

- **Не теряй нить в пикселях.** Назначение и поведение — раньше формы (форма — последние 5%).
- **Не тащи балласт-зависимости.** Бери паттерн, строй лёгким сам. Каждый вендор подтачивает простоту-ров.
- **Не давай ПО работать на тебя в минус.** Инструментируй, автоматизируй, используй инженера на высоком рычаге (аудит/ресёрч/фича целиком), а не как наборщика.
- **Не плоди пересекающиеся инструменты/действия.** Чистые границы + дерево решений, иначе агент/код путается.
- **Не доставай человека окнами-уточнениями.** Действуй по лучшему предположению, докладывай что сделал.
- **Каждый цикл — новая СИЛА, а не шероховатость.** Иначе бег на месте.
